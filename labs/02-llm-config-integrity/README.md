## Цель и область проверки

Я реализовал механизм контроля целостности конфигурации LLM: перед сборкой и запуском я сверяю SHA256 копии Modelfile с заранее зафиксированным эталоном. Я проверил два сценария: изменённый файл блокирует сборку и запуск через скрипт, а исходный файл проходит проверку, создаёт модель и открывает чат.

Я рассматривал изменение конфигурации после её одобрения. Для проверки обнаружения изменения я добавил в копию безвредный комментарий. Этот эксперимент проверяет контроль байтов файла и порядок вызовов Ollama; злонамеренную конфигурацию и production-систему я здесь не проверял. Реальные банковские данные я не использовал. `DEMO-4827` из первого кейса остаётся вымышленным **тестовым секретом**.

## Что я сделал

Я выполнял команды в локальной папке эксперимента. Сначала я сохранил конфигурацию существующего `neobank-lab` и рассчитал хэш:

```powershell
ollama show neobank-lab --modelfile | Out-File -FilePath .\neobank-baseline.Modelfile -Encoding utf8
Get-FileHash -LiteralPath .\neobank-baseline.Modelfile -Algorithm SHA256
```

Я получил и зафиксировал эталон:

```text
66EC48B1E589ABD150F61EEAEE7D47DE1D22FDA0F53963AEC81E56AF9A298CF9
```

Затем я создал копию и добавил в неё комментарий:

```powershell
Copy-Item .\neobank-baseline.Modelfile .\neobank-modified.Modelfile
Add-Content -LiteralPath .\neobank-modified.Modelfile -Value '# Integrity test: modified copy' -Encoding utf8
```

Я проверил равенство хэшей исходного файла и изменённой копии:

```powershell
(Get-FileHash .\neobank-baseline.Modelfile).Hash -eq (Get-FileHash .\neobank-modified.Modelfile).Hash
```

Я получил `False`: хэши различаются. Затем я сравнил оба файла с тем же зафиксированным эталоном:

```powershell
(Get-FileHash -LiteralPath .\neobank-baseline.Modelfile -Algorithm SHA256).Hash -eq '66EC48B1E589ABD150F61EEAEE7D47DE1D22FDA0F53963AEC81E56AF9A298CF9'
(Get-FileHash -LiteralPath .\neobank-modified.Modelfile -Algorithm SHA256).Hash -eq '66EC48B1E589ABD150F61EEAEE7D47DE1D22FDA0F53963AEC81E56AF9A298CF9'
```

Для исходного файла я получил `True`, для изменённой копии — `False`. Я обнаружил изменение файла даже при добавлении комментария, не меняющего назначение конфигурации.

## Как работает реализованный механизм

В [скрипте](Start-VerifiedNeoBank.ps1) я сохранил исторический эталон в `$expectedHash`. По умолчанию `$ModelFile` указывает на `neobank-baseline.Modelfile` рядом со скриптом через `$PSScriptRoot`.

1. Я создаю временный файл и копирую в него выбранный Modelfile.
2. Я вычисляю SHA256 **этой копии** и сравниваю его с эталоном.
3. При несовпадении я выбрасываю ошибку `SHA256 mismatch. Model creation and launch blocked.`; скрипт завершает работу с кодом 1 до вызовов сборки и запуска.
4. При совпадении я передаю **тот же временный файл** в `ollama create neobank-verified -f ...`. Если команда сборки возвращает ненулевой `$LASTEXITCODE`, скрипт блокирует запуск.
5. В `finally` я удаляю временный файл. После успешной сборки я вызываю `ollama run neobank-verified`; скрипт возвращает код завершения этой команды.

Так я сокращаю промежуток между проверкой и использованием конфигурации. Абсолютную защиту от конкурентного изменения файлов этот подход не обеспечивает: временный файл не блокируется от записи на весь период проверки и чтения Ollama. Отдельно остаётся возможность конкурентной замены именованной модели между сборкой и запуском.

Я публикую именно версию скрипта, использованную в эксперименте. Проверку ветви ошибки сборки Ollama, отсутствующего файла и конкурентных изменений в пять результатов ниже я не включаю: отдельных результатов этих сценариев у меня нет.

## Проверки и результаты

Мой первый запуск остановила политика выполнения PowerShell. Это ограничение запуска `.ps1`, а не результат проверки SHA256. Для отдельного процесса я использовал `-ExecutionPolicy Bypass`; постоянную политику системы я не изменял.

**Отрицательный сценарий:**

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "$HOME\ai-security-lab\Start-VerifiedNeoBank.ps1" -ModelFile "$HOME\ai-security-lab\neobank-modified.Modelfile"
```

Я получил `SHA256 mismatch. Model creation and launch blocked.` Создание и запуск модели через скрипт были заблокированы.

**Положительный сценарий:**

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "$HOME\ai-security-lab\Start-VerifiedNeoBank.ps1"
```

Я получил `Integrity check passed.`, сообщения сборки до `success`, после чего открылся чат. Я завершил его командой `/bye`. Доступные строки я сохранил в [evidence.md](evidence.md) как выдержки.

| test_id | Проверка | Ожидал | Получил | Статус |
| --- | --- | --- | --- | --- |
| I01 | Равны ли хэши исходного и изменённого файлов? | False | False | PASS |
| I02 | Совпадает ли исходный файл с эталоном? | True | True | PASS |
| I03 | Совпадает ли изменённый файл с эталоном? | False | False | PASS |
| I04 | Сборка и запуск через скрипт с изменённым файлом | blocked | blocked | PASS |
| I05 | Сборка и открытие чата через скрипт с исходным файлом | launched | launched | PASS |

Те же пять проверок я записал в [results.csv](results.csv) с полями `test_id,check,expected,actual,status`. В I01 `False` — результат **сравнения на равенство**, то есть ожидаемое обнаружение различия. `PASS` означает совпадение ожидаемого и фактического результата конкретной проверки, а не общую оценку безопасности модели.

## Выводы и ограничения

Я реализовал контроль целостности экспортированной конфигурации перед её использованием и проверил его на исходном файле и копии с добавленным комментарием. Я обнаружил изменение по SHA256 и получил блокировку сборки и запуска через скрипт; исходный файл прошёл проверку и позволил открыть чат.

- Я проверял экспортированный **Modelfile**, а не содержимое файлов весов. Изменение alignment и весов в этой работе я не проводил.
- Хэш фиксирует байты: комментарии, кодировка и окончания строк тоже влияют на результат. В Windows PowerShell `Out-File -Encoding utf8` сохраняет UTF-8 с BOM; при повторении в другой оболочке байты могут отличаться.
- Сам по себе хэш не определяет безопасность содержимого. Одобрение конфигурации и контроль её неизменности — разные действия.
- Эталонный хэш и скрипт должны быть защищены от изменения. Их защиту правами доступа или подписью я здесь не реализовал.
- Скрипт можно обойти прямым запуском Ollama; принудительный контроль доступа я не реализовал.
- Временная копия не обеспечивает абсолютную защиту от конкурентной записи. Именованная модель `neobank-verified` также не защищена от конкурентной замены между сборкой и запуском.
- Экспорт содержит локальную ссылку на blob модели, поэтому файл не является полностью переносимым. Проверка Modelfile не подтверждает неизменность содержимого blob по этой ссылке.
- Проверка целостности не устраняет утечки тестового секрета из [первого кейса](../01-neobank-secret-leakage/README.md). Повторную проверку устойчивости к запросам из первого кейса я в этом эксперименте не проводил.
- Я не проверял защиту от всех подмен моделей и не оценивал безопасность production-инфраструктуры. Устранение jailbreak по этим результатам я не заявляю.
- Точные байты baseline не опубликованы; по репозиторию нельзя независимо пересчитать исторический хэш. Выдержки вывода не заменяют полный терминальный лог.

## Воспроизведение на другом компьютере

Исторический хэш в опубликованном скрипте я сохраняю как часть эксперимента. Файл с этим хэшем я не реконструирую. Для собственного прогона нужен собственный проверенный baseline.

1. Подготовьте `neobank-lab` по [первому кейсу](../01-neobank-secret-leakage/README.md). Установленная локальная модель должна быть доступна Ollama.
2. Откройте **Windows PowerShell** в папке `labs/02-llm-config-integrity/` вашего checkout. Убедитесь, что там находится `Start-VerifiedNeoBank.ps1`. Экспортируйте конфигурацию:

   ```powershell
   ollama show neobank-lab --modelfile | Out-File -FilePath .\neobank-baseline.Modelfile -Encoding utf8
   ```

3. Проверьте и одобрите содержимое экспорта, включая `FROM`, системную инструкцию и параметры. Например, откройте файл для чтения:

   ```powershell
   Get-Content -LiteralPath .\neobank-baseline.Modelfile
   ```

4. Рассчитайте SHA256 одобренного файла:

   ```powershell
   Get-FileHash -LiteralPath .\neobank-baseline.Modelfile -Algorithm SHA256
   ```

5. В **локальной копии** `Start-VerifiedNeoBank.ps1` вручную замените значение `$expectedHash` на собственный проверенный SHA256. Не подставляйте текущий хэш автоматически при каждом запуске: это уничтожит смысл сравнения с доверенным эталоном. Этот шаг создаёт вашу конфигурацию проверки и не воспроизводит исторические байты исходного экспорта.
6. Создайте изменённую копию:

   ```powershell
   Copy-Item .\neobank-baseline.Modelfile .\neobank-modified.Modelfile
   Add-Content -LiteralPath .\neobank-modified.Modelfile -Value '# Integrity test: modified copy' -Encoding utf8
   ```

7. Повторите отрицательный и положительный сценарии из текущей папки:

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File .\Start-VerifiedNeoBank.ps1 -ModelFile .\neobank-modified.Modelfile
   powershell -NoProfile -ExecutionPolicy Bypass -File .\Start-VerifiedNeoBank.ps1
   ```

   В отрицательном сценарии ожидается сообщение о несовпадении SHA256 до сборки и запуска. В положительном — проверка, успешная сборка и открытие чата; завершите чат через `/bye`. Параметр `-ExecutionPolicy Bypass` относится к отдельному процессу; постоянная политика системы этими командами не меняется. Запишите собственные результаты отдельно от исторического CSV.

## Будущие улучшения

Отдельно я планирую рассмотреть защиту эталона и скрипта от изменения, ограничение прямого доступа к Ollama, контроль содержимого весов и защиту от конкурентной замены временного файла и модели.
